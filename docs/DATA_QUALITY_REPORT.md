**How to read it**

* **Every line is accounted for.** Read = unreadable + exact duplicates + rejected + superseded + loaded,
  for both entities. The pipeline checks this on every run and fails if it does not hold.
* **Rejections cascade, deliberately.** Of the 76 orders rejected as `customer_unknown`, 49 point at customer
  ids that never existed (`C90xxx`), and 27 belong to the 6 customers whose CRM record lost its `customer_id`.
  Loading those orders would break referential integrity; they sit in quarantine and load automatically on a
  later run once the customer record is fixed upstream (covered by `test_orphan_order_loads_once_its_customer_arrives`).
* **High correction rates are mostly cosmetic.** Status casing (`SHIPPED ` → `shipped`), non-ISO dates and
  country spellings (`United States` → `US`) account for most corrections. They are counted because they show how
  much normalization the sources need, which is a conversation to have with the source owners.
* **The single biggest fixable loss is `currency_missing` (74 orders).** The pipeline does not guess a currency.
  If the business confirms currency can be derived (for example from the customer's country), it is a one-rule
  change; until then a guessed currency would silently corrupt revenue figures.
* **Warnings are loaded, not dropped.** 24 orders have an unrecognized status (stored as `unknown`), 7 customers
  have an unparseable signup date, 5 an invalid email. Each is filterable via `dq_flags`.
